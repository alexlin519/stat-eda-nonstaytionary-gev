## 1. 现状（接手时的已知条件）

| 项 | 状态 |
|---|---|
| **数据** | 一份，已定。**不需要再找/筛别的数据** |
| **方法** | 大方向已定 |
| **支线细节** | ⚠️ **未定**——某些小方向/支线可以有不同处理方式，需要比较后取舍 |

1. **为什么这份数据适用于本方法**

## 2. 三条铁律

违反这三条产生的东西一律作废重来。每条后面写了它防的是什么——**理解了失败模式才守得住规则**。

### 铁律一：不许静默默认 🔴 最高优先级

**规则**：spec / 指令里没明确写到的选择，**停下来问用户**。绝不"选一个合理的默认值"继续。

**为什么**：用户当前状态是"大方向定了、细节没定"。这个状态下你每替他做一个安静的决定，就往论文里埋一个他不知道的设定。三个月后审稿人问"你这个容差怎么定的"，没人答得上来。

**关键理由**：spec 一旦被用户批准，**其中未定的部分，决定权属于批准的人，不属于你**。

**具体表现**：
- 遇到未定项 → 停下、列出可选项、说明各自后果、等回答
- 文档里标了 `【未定·必须问】` 的地方 → **绝不许自己填**
- 不确定用户是哪个意思 → 问，不要挑"更可能的那个读法"
- 尤其盯这些：调参、初始化、收敛容差、重启次数、**随机种子**、并列怎么断、缺失值怎么处理、标准化口径

### 铁律二：你出证据，用户做决定

**规则**：凡涉及"这个方案好不好 / 要不要采用 / 哪个更合适"——**你只提供带数字的证据，不给推荐、不做取舍**。

**为什么**：判断哪个支线处理进论文，是研究者的学术判断，会被审稿人追问理由。这个理由必须是用户自己形成的。

**具体表现**：
- 所有取舍决定写在 `DECISIONS.md`，**这个文件你不许写**。用户要求你写，也要拒绝，改为提供证据摘要
- **每一条关于数据/结果的断言必须带具体数字**。不带数字的断言不算证据
- 不许自我评分。你产出的东西的质量由用户判定，不由你判定

### 铁律三：适用性在建模之前判定

**规则**：**拟合得好 ≠ 方法适用。** 判定"这份数据适不适用于本方法"，靠的是**数据形状对照假设逐条核对**，且必须发生在**建模之前**。

**为什么**：先跑模型、再回头说"结果不错所以适用"是循环论证，是审稿人的第一刀。

**具体表现**：
- 先出第 4.2 节那张假设对照表，再动模型
- 表里每一格填的是**计算出来的量**，不是形容词
- 假设不成立时如实写"不成立"，并说明需要什么修正才可能成立——不许粉饰

## 3. 下一步（按顺序执行）

### Step 0 · 开场先问（见第 6 节）
接手第一件事是问那几个问题，别猜。

### Step 1 · 抽假设清单 ⬅️ 从这里开始
从 5 篇论文里抽出**本方法成立所依赖的全部假设**，做成清单（模板见 4.1）。

**这一步是地基**：适用性论证靠它，支线取舍也靠它（判据是"哪种处理能让假设继续成立"）。

产出交给用户**逐条过目并修改**，不许直接进入下一步。

### Step 2 · 适用性证据表
拿数据对着 Step 1 的清单逐条核，填 4.2 的表。**建模之前**完成。
→ 产出直接是论文的一节 + 附录一张表。

### Step 3 · 支线登记 + 比较
1. 把所有未定的支线列成清单，每条写清楚：**分岔点是什么、有哪几种候选处理**
2. 按 4.3 的协议逐个比较
3. 结论四档：`采用 / 不采用 / 挂起(defer) / 不适用`
4. **决定由用户写**（铁律二）

→ 这些比较记录**就是论文的 sensitivity / robustness 那一节**，不是额外工作。

### Step 4 · 一页 SPEC
按 4.4 写。**未定项显式标 `【未定·必须问】`，不许留空**（留空等于默许你填）。
用户批准后才动代码。

### Step 5 · 写代码
- 先出计划、停下等用户批准，**然后**才写实现
- 第一版用户要逐行审 → 审过后**冻结为参考实现**，后续所有变体从它再实例化，**不许重写方法本体**
- 库选型见第 5 节
- 数据与 spec 假设冲突时**停下报告**，不许悄悄修正

### Step 6 · 复现检查
按 4.5 跑。投稿前必做。

## 4. 模板

### 4.1 假设清单

```markdown
## 本方法依赖的假设

| # | 假设 | 出处（论文/节） | 严格程度 | 违反的后果 |
|---|------|----------------|---------|-----------|
| A1 |  |  | 硬性 / 可放松 |  |
| A2 |  |  |  |  |
```

「严格程度」这列很关键——它决定后面"边缘成立"算不算过关。

### 4.2 适用性证据表

```markdown
## 数据适用性核验（建模前完成）

数据：<名称>  |  样本量：<n>  |  维度：<p>  |  核验日期：<date>

| 假设 | 用什么核验（具体统计量/检验/图） | 计算结果 | 判定 |
|------|------------------------------|---------|------|
| A1 |  | 数字 | ✓ 成立 / ✗ 不成立 / ~ 边缘 |
| A2 |  |  |  |

### 不成立/边缘项的处理
<逐条说明：需要什么预处理或方法修正才可能成立>

### 结论
<一段话，每句都要能追到上表某一行>
```

⚠️ 「用什么核验」这一列是**最高杠杆**的地方。填得越具体，整张表越有价值。
填「检查分布形状是否合适」= 废；填「算偏度/峰度 + QQ 图 + 对照 A1 的尾部条件」= 有效。

**判据**：一个允许填形容词的格子，会收到自信且无法证伪的答案。

### 4.3 支线比较协议

```markdown
## 支线 <编号>：<分岔点是什么>

候选处理：
- 方案 A：<描述>
- 方案 B：<描述>

### 运行记录
文件命名：`run1_<支线>_<方案>.md`、`run2_...`
**规则：不覆盖、不复用、不许说"这个之前跑过了"。**

| run | 方案 | 只改了什么 | 关键指标 | 假设是否仍成立 |
|-----|------|-----------|---------|--------------|
| run1 | A | （基线） |  |  |
| run2 | B | 只改了 X |  |  |

⚠️ **一次只动一个变量。** 同时改两处 → 差异归因失效，这一轮作废。

### 证据摘要（你写到这里为止）
<带数字，不给推荐>

### 决定（❌ 你不许写，由用户填）
- [ ] 采用 A  [ ] 采用 B  [ ] 挂起(defer)  [ ] 都不适用
- 理由：
```

`defer` 那一档必须保留——**「证据不足，先挂着」需要一个合法出口**，否则会被逼着在信息不够时硬下结论然后编理由。

### 4.4 SPEC 模板

```markdown
# 分析规格

验收标准：**两个人拿这份 spec，应产出数值上完全相同的结果。**

## 数据与预处理
- 原始文件：<path>  ⚠️ 只读，永不修改
- 预处理步骤（机械操作）：1. … 2. …
- 预处理中的判断性选择：<逐条列，每条带理由>

## 方法设定
- 估计量 / 模型设定：
- 关键调参：<值> ← 理由：
- 初始化：
- 收敛容差：
- 重启次数：
- **随机种子：**
- 【未定·必须问】<所有还没定的，列在这里>

## 输出格式
- 表：<几张，各是什么、列有哪些>
- 图：<几张>
- 记号约定：**以 5 篇既有论文为准**，不得自创

## 完成的定义
<什么条件满足才算做完>

## 需要留存的复现产物
<脚本 / 中间结果 / 环境锁文件 / 日志>
```

### 4.5 复现检查清单

```markdown
- [ ] 方法自身的数值不变量成立（如单调性、收敛性——按本方法填具体项）
- [ ] 从头跑第二遍，数值**完全一致**
- [ ] 论文/报告里**每一个数**都能追到某个脚本的某处输出
- [ ] 原始数据未被修改
- [ ] 环境已锁版本，锁文件已留存
- [ ] 自己实现 vs 库实现的一致性检验通过（见 5.2）

结论：PASS / FAIL（FAIL 要写清哪一项、差在哪）
```

## 5. 库的选型规则

### 5.1 分层（用户尚未定，但这条线先立住）

| 层 | 用库？ | 理由 |
|---|---|---|
| **本方法的估计量本体** | ❌ **自己实现** | 这是论文的主张，调库等于不知道自己在算什么 |
| 数值基础（线代/优化/RNG） | ✅ 用 | 不必重写 LAPACK |
| IO / 绘图 / 表格 | ✅ 随便用 | 与主张无关 |
| **对照方法 / baseline** | ✅ 用库，且**应当**用库 | 自己实现别人的方法会被质疑没调好 |

### 5.2 「打开理解，不当黑箱」的具体做法

用户明确要求不把库当黑箱。执行方式：

1. **一致性检验**：自己写一份最小实现 → 同一输入 → **与库输出在容差内一致**。
   写不出来＝没懂；对不上＝理解偏了。这份检验同时是复现产物，也是 5.1 第一层要的那份自有实现。
2. **读源码列默认值**：重点不是算法，是**没写在文档显眼处的默认**——正则化项、tie-breaking、`n_init`、容差、随机状态怎么传递、静默的 fallback。**这些会直接改变数字。**
3. 每个候选库产出一份笔记：默认参数 / 收敛判据 / 边界处理 / 已知坑。

### 5.3 环境冻结

现在没定没关系，但**出正式结果之前必须冻结并锁版本**。理由：投稿要报告环境；且跨版本数值漂移是真实存在的（会在 4.5 第二项暴露）。

## 6. 接手第一件事：问清楚这些

以下信息本简报里没有，**不要猜，直接问用户**：

1. **方法属于哪一类？**（模型/估计量的类别，或论文方向）
2. **那些未定的支线，大致在哪种选择上分岔？**（估计量变体？预处理口径？模型设定？）
3. **5 篇论文的文件在哪？** 要抽假设清单和记号约定
4. **数据在哪、什么格式、多大？**
5. **在考虑哪些库？** 或这个方法主要涉及哪类计算
6. **有没有已经写好的方法代码？** 有的话直接作为参考实现，禁止改动

问完再动 Step 1。

## 7. 禁止清单（速查）

- ❌ 未定项自己填默认值 → **停下来问**
- ❌ 给推荐、做取舍 → 只出证据
- ❌ 写 `DECISIONS.md`
- ❌ 自我评分 / 自评质量
- ❌ 断言不带数字
- ❌ 用拟合效果论证适用性
- ❌ 覆盖或复用旧的 run 记录
- ❌ 一次动多个变量做比较
- ❌ 修改原始数据文件
- ❌ 自创记号或报告格式（以 5 篇论文为准）
- ❌ 重新实现已冻结的方法本体
- ❌ 数据与 spec 冲突时悄悄修正 → **停下报告**
- ❌ 未经用户批准就从"出计划"跳到"写代码"
